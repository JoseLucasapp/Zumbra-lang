# Zumbra 0.14.3 runtime memory hot-loop fix

This patch keeps the public CLI version at `0.14.3` and adds an explicit native runtime memory lifecycle for long-running native programs.

The native runtime now tracks allocation sizes, active bytes, peak bytes and frees. It also exposes these native builtins:

- `runtimeMemoryMark()` returns a lightweight allocation mark.
- `runtimeMemoryReset(mark)` releases tracked allocations created after that mark, clears bound-method caches that could point to released temporary receivers, and is typed as `null` because it is a side-effect operation intended for hot-loop statements.
- `runtimeMemoryResetPeak()` resets the peak byte counter to the current active bytes.
- `runtimeMemoryStats()` returns allocation counters and active/peak byte snapshots.

This is intentionally explicit. Programs that run continuous hot loops can keep persistent state outside a mark, allocate temporary values inside the loop, and reset back to the mark after each slice/frame. This prevents temporary structs, arrays, dictionaries and strings from surviving until process shutdown.

Validation:

```bash
rm -rf build nativec/build
mkdir -p build
go build -o build/zumbra .
ZUMBRA_BIN=./build/zumbra scripts/test-0.14.3-runtime-memory-hotloop.sh
```

Expected output includes:

```text
runtime-memory-hotloop: ok
```

## 0.14.3-v2 symbol registration fix

The runtime memory APIs are now registered in `builtinspec`, `types`, and the native C backend. This prevents `zumbra build --release` from rejecting `runtimeMemoryMark`, `runtimeMemoryReset`, `runtimeMemoryResetPeak`, and `runtimeMemoryStats` during semantic resolution.


## 0.14.3 runtime memory type fix

`runtimeMemoryReset(mark)` is now registered as a `null`/side-effect builtin instead of `u64`. This prevents desktop app pipelines from rejecting statement-only reset calls inside conditional branches with `types: function has conflicting return types: u64 and null`.

## v4 checker fix

The type checker now treats `if`/`match` used as standalone statements as statement-only control flow. Branch result types are still unified when the `if`/`match` is the final expression of a block/function, but ordinary statement usage no longer fails with false conflicts such as `u64 and null`. This keeps desktop app pipelines from failing when one branch ends with a value-producing runtime call and the other branch has no value.
